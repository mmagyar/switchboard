Declare the contract once

TypeScript starts with a runtime Zod schema and infers the type. Rust starts with serde/schemars structs and generates runtime schemas when a typed route is constructed.

TypeScript · schema first

import { z } from "zod";
import {
  define, RouteHandlerDefiner,
  Router, NotFoundError,
} from "switchboard/server";

const cocktailSchema = z.object({
  slug: z.string(),
  name: z.string(),
});
type Cocktail = z.infer<typeof cocktailSchema>;

const def = define<"public">();

Use this setup for the TypeScript fragments below.

Rust · type first

use serde::{Deserialize, Serialize};
use schemars::JsonSchema;
use switchboard::{
    Authorization, DefinitionError,
    HandlerDefiner, HttpError, Method,
    Router, TypedRoute,
};

#[derive(Clone, Serialize, Deserialize, JsonSchema)]
struct Cocktail { slug: String, name: String }

#[derive(Clone, Serialize, Deserialize, JsonSchema)]
struct DetailParams { slug: String }

#[derive(Clone, Serialize, Deserialize, JsonSchema)]
struct NoParams {}

Use these imports and models for the Rust fragments below.

The declaration direction changes. Both still validate untrusted input at runtime. Rust's generated schema supports a defined subset of JSON Schema; unsupported constraints fail explicitly. Use a Rust refinement for application-specific validation.

Give the route a reusable name

Keep the JSON detail contract separate from HTML formatting. Reuse it in the server and client. The Rust factory creates a fresh definition because binding consumes its route.

TypeScript · route builder

const detailDef = def.get(
  "/cocktails/:slug",
  "public",
  cocktailSchema,
  z.object({ slug: z.string() }),
);

Rust · typed route factory

fn detail_route() -> Result<
    TypedRoute<DetailParams, (), Cocktail, &'static str>,
    DefinitionError,
> {
    TypedRoute::new(
        Method::Get, "/cocktails/:slug",
        "public", vec![],
    )
}
Path and query share params
Add q: z.string().optional() or a Rust q: Option<String> to the params contract for ?q=lime.
Shorthand is available
TypeScript can omit the params override. Rust can use switchboard::route!(get, "/cocktails/:slug", "public", Cocktail)? to infer a params type.
Prefixes stay server-only
Pass ["en", "de"] as the final TypeScript builder argument, or vec!["en".into(), "de".into()] to Rust. Client URLs keep the canonical path.

Optional path params use :slug? and follow required params. Names ending in Id infer numbers in both shorthand APIs; Rust also recognizes _id. Prefer strings for opaque identifiers.

Make public access an explicit decision

The bar app currently grants public access. The permission label constrains declarations; your authorization callback decides whether a request is allowed.

TypeScript · authorizer, then user resolver

const defineRoute = RouteHandlerDefiner(
  async (_user, permission, _request) =>
    permission === "public" ? "ok" : "forbidden",
  async (_request) => null,
);

Rust · user resolver, then authorizer

fn public_definer()
    -> HandlerDefiner<(), &'static str>
{
    HandlerDefiner::new(
        |_| async { Ok(()) },
        |(), permission, _| async move {
            Ok(if permission == "public" {
                Authorization::Ok
            } else {
                Authorization::Forbidden
            })
        },
    )
}

The constructor order reverses. Both resolve the user before authorizing, and authorize before parsing the body. For protected routes, replace these public-only callbacks with verified session resolution and permission checks. Unauthenticated maps to 401; forbidden maps to 403.

Bind the handler and return a typed value

Without a formatter, Switchboard produces JSON. These small handlers use illustrative data so the library boundary is visible. Replace the local lookup with the app's storage adapter.

TypeScript · async value or thrown HTTP error

const detail = defineRoute(
  detailDef,
  async ({ slug }) => {
    if (slug !== "daiquiri") {
      throw new NotFoundError();
    }
    return { slug, name: "Daiquiri" };
  },
);

const router = new Router();
router.addRoute(detail);

Rust · async Result

let define = public_definer();
let detail = define.bind_typed(
    detail_route()?,
    |params, _body, (), _prefix| async move {
        if params.slug != "daiquiri" {
            return Err(HttpError::not_found());
        }
        Ok(Cocktail {
            slug: params.slug,
            name: "Daiquiri".into(),
        })
    },
);

let mut router = Router::new();
router.add_route(detail)?;

Rust keeps one handler shape: (params, Option<body>, user, prefix), including GET with None. TypeScript GET uses (params, user, prefix); POST adds body after params. Both register method/path from the route object and reject duplicates.

Use TypeScript RequestError/Unauthorized or Rust HttpError::new/HttpError::unauthorized for other HTTP failures. The Rust statements shown throughout belong inside functions returning a compatible Result, so ? can propagate errors.

Search with a normal HTML form

The app accepts ingredient selections at POST /cocktails. This is a search, not cocktail creation. Unchecked groups are absent, one checked value is a string and repeated names become arrays.

TypeScript · optional scalar-or-array fields

const oneOrMany = z.union([
  z.string(), z.array(z.string()),
]);
const selectionSchema = z.object({
  drink_ids: oneOrMany.nullish(),
  additive_ids: oneOrMany.nullish(),
});
const searchDef = def.post(
  "/cocktails", "public",
  selectionSchema,
  z.array(cocktailSchema),
);

const search = defineRoute(
  searchDef,
  async (_params, body) => findCocktails(body),
);

Rust · untagged enum, optional fields

#[derive(Clone, Serialize, Deserialize, JsonSchema)]
#[serde(untagged)]
enum OneOrMany {
    One(String),
    Many(Vec<String>),
}

#[derive(Clone, Serialize, Deserialize, JsonSchema)]
struct Selection {
    drink_ids: Option<OneOrMany>,
    additive_ids: Option<OneOrMany>,
}

let search_def = TypedRoute::<
    NoParams, Selection, Vec<Cocktail>, _,
>::new(Method::Post, "/cocktails", "public", vec![])?;

let search = define.bind_typed(
    search_def,
    |_params, body, (), _prefix| async move {
        let selection = body.ok_or_else(||
            HttpError::new(400, "Missing selection"))?;
        find_cocktails(selection).await
    },
);

findCocktails and find_cocktails are app-owned matching adapters, returning Cocktail[] and Result<Vec<Cocktail>, HttpError>. Normalize scalar/array values and validate IDs there. This adapted JSON body uses .nullish() to match Rust Option's missing-or-null fields; native forms leave unchecked groups absent. The original app uses .optional(), which excludes explicit JSON null. Register the search handler with the same router used above.

Shared browser markup · no application script required

<form action="/cocktails" method="post">
  <label>
    <input type="checkbox" name="drink_ids" value="white-rum">
    White rum
  </label>
  <button type="submit">Find cocktails</button>
</form>

The app's homepage actually uses GET; both GET and POST search routes exist. This POST variant uses the declared body contract. An HTML formatter must render the results for normal page navigation. POST defaults to 201 in both implementations, including search; set an explicit 200 in the formatter if that is your policy.

Render HTML on the server

The bar app uses React's server renderer without React hydration. Rust can use optional Maud. Both escape ordinary text interpolation and can send complete HTML with no application JavaScript or WASM.

TypeScript · formatter returns data and headers

import { createElement } from "react";
import { renderToString } from "react-dom/server";

const htmlDetail = defineRoute(
  detailDef,
  async ({ slug }) => ({ slug, name: "Daiquiri" }),
  (data) => ({
    data: renderToString(
      createElement("main", null,
        createElement("h1", null, data.name)),
    ),
    headers: new Headers({
      "Content-Type": "text/html; charset=utf-8",
    }),
    status: 200,
  }),
);

Rust · formatted binding uses deferred values

use switchboard::{DeferredValue, Formatted};
use switchboard::render::html;

let html_detail = define.bind_formatted(
    detail_route()?.definition,
    |params, _body, (), _prefix| async move {
        Ok(DeferredValue::ready(serde_json::json!({
            "slug": params["slug"],
            "name": "Daiquiri",
        })))
    },
    |data, (), _request, _params| async move {
        let value = data.resolve().await?;
        let name = value["name"].as_str()
            .ok_or_else(HttpError::internal)?;
        let markup = html! { main { h1 { (name) } } };
        let mut out = Formatted::with_body(
            markup.into_string(),
        );
        out.headers.insert(
            http::header::CONTENT_TYPE,
            http::HeaderValue::from_static(
                "text/html; charset=utf-8"),
        );
        out.status = Some(200);
        Ok(out)
    },
);

Typed JSON and formatted HTML use different Rust bindings. bind_typed has no formatter argument. bind_formatted takes RouteDef and dynamic JSON/deferred values. Here, .definition converts the typed declaration. Register either the JSON detail handler or this HTML alternative at the canonical path, not both.

The Rust example enables switchboard's maud feature and declares direct maud = "0.27", http = "1" and serde_json = "1" dependencies. The html! macro resolves the Maud crate in the consuming application. The TypeScript renderer is app-owned, not a Switchboard export. The app's broader formatOutput helper chooses HTML or JSON from Accept; negotiation is an application policy. Typed clients below need JSON, so keep the JSON binding or implement that negotiation in your formatter.

Call the JSON route with its contract

Use the canonical route definition to build URLs, validate output and infer the result type. Empty successful responses can produce undefined or None.

TypeScript · callable client

import { createClient } from "switchboard/client";

const api = createClient("http://127.0.0.1:8080");
const cocktail = await api(
  detailDef,
  { slug: "daiquiri" },
);
// Cocktail | undefined

Rust · native client

use switchboard::{
    ApiClient, CallSettings, ClientOptions,
};

let client = ApiClient::new(
    "http://127.0.0.1:8080",
    ClientOptions::default(),
)?;
let cocktail = client.call(
    &detail_route()?,
    &DetailParams { slug: "daiquiri".into() },
    None,
    CallSettings::default(),
).await?;
// Option<Cocktail> inside Result error handling

The native client needs an absolute base URL. It has no browser CORS/SameSite context. TypeScript maps HTTP, transport and malformed-JSON failures to ApiError. Output-schema mismatches throw ZodError; caller serialization and callback errors can also propagate. Rust returns typed client errors. HTTP failures, network status 0 and invalid-response status 502 remain distinguishable. A client validation failure is separate from a server-side output warning.

Keep deferred work deferred

A formatted handler can return fields that are still pending. The formatter receives them before the whole result resolves, so an application renderer can stream an early shell and later content.

TypeScript · handler return fragment

return {
  slug: "daiquiri",
  name: Promise.resolve("Daiquiri"),
};
// formatOutput receives the unresolved name.
// It can return a ReadableStream as data.

Rust · handler return fragment

Ok(DeferredValue::object([
    ("slug".into(), DeferredValue::ready("daiquiri")),
    ("name".into(), DeferredValue::future(async {
        Ok(DeferredValue::ready("Daiquiri"))
    })),
]))
// A formatter can return a Body::from_stream(...)
// through Formatted::with_body(...).

These are deferred-output fragments, not complete stream renderers. The HTML examples above resolve everything before sending. A real streaming formatter must retain individual fields and construct the stream. Ordinary JSON awaits the full result. Background output validation warns on mismatches; a late failure cannot replace headers already sent.

Rust futures own Send + 'static values. Retain a definer owner for validation work. On shutdown, stop the server, then await define.drain_background() to finish or define.cleanup_background() to abort and join pending validation.

Choose a host separately from the routes

The nearby app deploys to Cloudflare Workers. Its fetch adapter calls router.handleRequest(request). Bun is its tooling runtime. The following alternative hosts use Bun's server and the Rust native server.

TypeScript · Bun hosting alternative

import { serveHotBuns } from "switchboard/server";

const reload = await serveHotBuns(
  { port: 8080 },
  router,
);
// During shutdown:
reload.stop();

This replaces the Workers adapter; it is not Workers-compatible hosting.

Rust · owned native server

use std::sync::Arc;
use switchboard::server::{serve, ServerConfig};

let mut server = serve(
    ServerConfig {
        hostname: "127.0.0.1".into(),
        port: Some(8080),
        ..Default::default()
    },
    Arc::new(router),
    Default::default(),
).await?;

// Await the application's shutdown signal here.
server.stop().await?;
define.drain_background().await?;

The native product runs without Bun, Node or an embedded JavaScript engine.

Rust code changes require rebuilding/restarting the executable. ServerHandle::reload() signals browsers; it is not Bun's module HMR. The native server also supports TLS and WebSocket upgrades. Set request-body, upload and concurrency policies for your application.

Add browser behavior only when you need it

Ordinary links, ingredient forms and server-rendered pages work without a client library, WASM or hydration. The JavaScript-free baseline is shared by both approaches.

HTML-only baseline
The browser follows links and submits forms. The server renders the next page. This guide itself uses only HTML and CSS.
TypeScript enhancement
Add app-owned DOM listeners or use createClient in browser JavaScript. React server templates do not require React hydration.
Rust enhancement
Compile optional browser code to WASM. Generated wasm-bindgen JavaScript bindings and a module bootstrap load it. Keep listeners and sockets in owned handles.
See optional browser client declarations

These fragments belong in the optional browser application. They are displayed as text here.

TypeScript · same-origin JSON client

import { createClient } from "switchboard/client";

const api = createClient("");
const cocktail = await api(
  detailDef,
  { slug: "daiquiri" },
);

Rust · optional switchboard-browser crate

use switchboard_browser::{
    BrowserClient, CallSettings, ClientOptions,
};

let client = BrowserClient::new(
    "", ClientOptions::default(),
);
let route = detail_route()?;
let cocktail = client.call_route(
    &route,
    &DetailParams { slug: "daiquiri".into() },
    None,
    &CallSettings::default(),
).await?;

Browser settings are borrowed in Rust; native settings are passed by value. Put this fragment in an async function with compatible error conversion. The browser crate disables core server/client features and uses browser fetch.

The measured Rust interactive demo downloads 178,861 gzip bytes of WASM, generated bindings and bootstrap, versus 66,684 gzip bytes for the comparable TypeScript client demo. Those are particular demo builds, not a mandatory per-page cost. HTML-only pages download neither. Browser startup, CPU and memory have not been measured.
